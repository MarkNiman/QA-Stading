# Git и CI для учебных проверок
[[Учебник QA|Все статьи]] · Предыдущая: [[Автоматизация без слепого копирования]]

**До начала:** [[JavaScript на модели очереди]]. **Цель:** сохранить проверяемую работу в отдельной ветке и понять запуск тестов на сервере. **Время:** 45–60 минут.

## Версия важна для QA
«Вчера работало» трудно воспроизвести. Commit SHA связывает отчёт с определённой версией. Но SHA не описывает локальные незакоммиченные изменения: вместе с ним нужен git status.

Команды ниже предназначены для обычного клона QA-Stading. Если ты используешь старую локальную папку, созданную до публикации через GitHub, сначала проверь её историю: она может отличаться от удалённой. Для упражнения удобнее новый клон в отдельной папке.

## Сначала посмотри состояние
```powershell
git status
git log -1 --oneline
git remote -v
```
status показывает изменения рабочего дерева и подготовленные файлы. log — историю. remote — адреса удалённых репозиториев.

Создай ветку для своей проверки:
```powershell
git switch -c study/queue-tests
```
Измени один тест из предыдущей статьи, затем посмотри diff. Добавляй конкретный файл, чтобы случайно не включить постороннюю работу:
```powershell
git diff -- labs/encounter.test.mjs
git add labs/encounter.test.mjs
git diff --cached
git commit -m "test: cover queue wrap for four participants"
```
Коммит фиксирует подготовленный снимок локально. push передаёт коммиты на сервер. Ветка с таким именем уже существует? Выбери новое имя после проверки status; не перезаписывай чужую работу.

## Что делает CI
CI запускает автоматические проверки при изменениях, например на pull request. Workflow состоит из jobs, а job — из steps. Runner — среда исполнения. Зелёный статус означает, что настроенные команды завершились успешно; качество требований и полнота сценариев остаются отдельными вопросами.

В labs/ci-example.yml показан учебный workflow с запуском node --test. Он хранится вне .github/workflows и поэтому сам не включён. Сначала изучи его и запусти проверки локально. Настройка CI остаётся практикой твоего этапа обучения.

## Как разбирать падение
Найди первую содержательную ошибку: среда не установилась, файл не найден или ожидание не совпало. Для последнего сравни вход, expected и actual. Перезапуск без анализа не объясняет причину.

## Попробуй
Поясни разницу между «тест не запустился» и «тест запустился и нашёл неверный раунд». Какие доказательства приложить к каждому?

> [!tip]- Самопроверка
> В первом случае нужны лог установки или команды и окружение; во втором — входные данные, сообщение assert и версия кода. Ошибка инфраструктуры не доказывает дефект игровой логики.
