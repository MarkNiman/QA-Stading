# Автоматизация без слепого копирования
[[Учебник QA|Все статьи]] · Предыдущая: [[SQL на бестиарии GRUNTWORK]] · Далее: [[Git и CI для учебных проверок]]

**До начала:** [[JavaScript на модели очереди]]. **Цель:** отличать исполнение действий от проверки поведения. **Время:** 45–60 минут.

## Что автоматизируем
Ручная проверка очереди задаёт данные, выполняет действие и оценивает результат. Автотест делает те же шаги программно. Сам по себе он не придумывает правильное ожидание и не доказывает полноту покрытия.

В нашем хранилище labs/encounter.test.mjs — модульные тесты чистой функции. Они не проверяют сервер, экран, авторизацию реального пользователя или сохранение RPG Codex.

## Уровни проверки
| Уровень | Игровой пример | Что может остаться незамеченным |
|---|---|---|
| Модульный | Индекс и раунд функции C1 | Ошибка кнопки или сетевого маршрута |
| API | Сервер отклоняет запрещённую роль | Экран не обновляется после ответа |
| E2E | Ведущий переключает ход в браузере | Редкая комбинация внутренних данных |

E2E означает проверку пользовательского потока через участвующие компоненты. Набор из тысяч кликов без проверки результата не становится полезным покрытием.

## Разберём фрагмент Playwright
Следующий пример — адаптационный эскиз. Имена элементов условные; запустить его против настоящего RPG Codex без настройки нельзя.
```ts
await page.getByRole('button', { name: 'Следующий ход', exact: true }).click();
await expect(page.getByTestId('active-participant')).toHaveText('Стражник');
await expect(page.getByTestId('round-number')).toHaveText('1');
```
await ожидает завершения асинхронной операции. locator описывает элемент. expect формулирует проверку. Веб-проверки вроде toHaveText повторяются до успеха или истечения таймаута. Это уменьшает зависимость от скорости обновления; произвольная пауза не даёт такой гарантии.

Здесь не показаны import, запуск приложения, создание боя, вход под нужной ролью и очистка данных. Без них фрагмент не является полным тестом.

## Как использовать ИИ
Передай ИИ подтверждённое требование, предусловия, выбранные случаи и реальные локаторы. Попроси объяснить каждое ожидание. Затем проверь, что тест падает при намеренном нарушении в учебной копии.

Не принимай сгенерированный green-run за доказательство. Тест может проверять текст из своего же mock-ответа или не дождаться нужного изменения. Важно понимать, какая часть системы реально исполнялась.

## Попробуй
Для двух участников с одинаковым именем объясни, почему проверка имени недостаточна. Предложи устойчивое наблюдаемое свойство.

> [!tip]- Самопроверка
> Нужно различать участников по ID или другому уникальному признаку. На экране можно проверять выбранную строку с устойчивым идентификатором и номер раунда; контракт доступности такого признака надо согласовать.

Готовность: можешь назвать ограничение каждого написанного теста.
